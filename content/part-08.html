Relationships & cross-filtering

Relationships decide how filters travel between tables. Get cardinality and direction right.

1. Cardinality

TypeMeaningUse
One-to-many (1:*)One row in the dimension matches many rows in the factThe default and recommended type (Customer → Sales)
One-to-one (1:1)Each row matches at most one row on the other sideRare; usually better to merge the two tables
Many-to-many (*:*)Duplicates on both sidesAvoid when possible; prefer a bridge table of unique keys

The “one” side needs a column with unique, non-blank values (check it with Column distribution). Both key columns must have the same data type.

2. Cross-filter direction

  • Single (default): the dimension filters the fact table. This is what you want almost always.
  • Both (bi-directional): filters flow both ways. Use sparingly: it can create ambiguous paths, wrong totals and slow queries. A common valid use is a many-to-many via a bridge, or a slicer that must filter other dimensions.
  • You cannot create circular relationship paths.

3. Active vs inactive and role-playing dimensions

Only one active relationship can exist between two tables (shown as a solid line). Others are inactive (dotted line). A role-playing dimension is one dimension used for several roles, for example a Date table related to OrderDate, ShipDate and DueDate.

// OrderDate relationship is active; ShipDate relationship is inactive
Sales by Ship Date =
CALCULATE (
    [Total Sales],
    USERELATIONSHIP ( Sales[ShipDate], 'Date'[Date] )
)
ApproachProsCons
One Date table + inactive relationships + USERELATIONSHIPOne date table to maintain, smaller modelOne role per measure; needs extra measures
Duplicate the Date table (Order Date, Ship Date)Slice by both roles at the same time; no extra DAXMore tables to maintain

4. Other things to know

  • Manage them in Model view or Modeling → Manage relationships. Auto-detect can create wrong ones: review them.
  • If fact rows have a key that is missing in the dimension, visuals show a (Blank) member for them (a referential integrity problem).
  • Filters flow from the “one” side to the “many” side; the arrow on the line shows the direction.
Exam trap“Keep current visuals by order date and add a measure by ship date” → inactive relationship + USERELATIONSHIP, not a second active relationship (Power BI will not allow it) and not bi-directional filtering.
Key takeaways
  • Default: one-to-many, single direction from dimension to fact.
  • One active relationship per pair of tables; activate others with USERELATIONSHIP.
  • Both direction and many-to-many are exceptions, not the rule.

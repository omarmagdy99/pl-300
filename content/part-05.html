Combine queries & build keys

Merge = add columns (horizontal). Append = add rows (vertical).

1. Merge queries — the join kinds

Join kindResult
Left OuterAll rows from the first table + matching rows from the second
Right OuterAll rows from the second table + matching rows from the first
Full OuterAll rows from both tables
InnerOnly rows that match in both tables
Left AntiRows in the first table with no match in the second
Right AntiRows in the second table with no match in the first
  • Select the matching column(s) in both tables (Ctrl-click for composite keys).
  • The merge adds a column of type Table — click the expand icon to pick the columns you need.
  • Fuzzy matching lets near-matches join (spelling differences).
  • Merge Queries as New leaves the originals untouched.

2. Append queries

Stacks rows of tables with the same (or similar) columns. Append Queries changes the current query; Append Queries as New creates a new query. Columns are matched by name; missing ones become null.

3. Reference vs Duplicate

ReferenceDuplicate
New query starts from the output of the original. Changes to the original flow through.Copy of all the steps. Independent afterwards.

Typical recipe to build a dimension table from a fact table: Reference the fact query → Remove other columns (keep the attributes) → Remove Duplicates on the key.

4. Keys and star schema

  • The “one” side of a relationship needs a unique, non-empty key (check with column distribution).
  • Create a key by merging columns (Merge Columns) or adding an Index Column (surrogate key).
  • Aim for a star schema: one narrow fact table surrounded by dimension tables.
Exam trap“Keep all rows from table A and bring data from B” → Left Outer with A first. “Rows in A that do not exist in B” → Left Anti. Merge adds columns; Append adds rows.
Key takeaways
  • Know all six join kinds and which table must be first.
  • Append as New keeps the sources intact.
  • Reference for dependent queries, Duplicate for independent copies.
